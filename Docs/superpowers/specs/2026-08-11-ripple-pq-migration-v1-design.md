# Ripple Post-Quantum Migration Profile v1 — Design Specification

**Date:** 2026-08-11  
**Status:** Approved under standing autonomous project authorization; isolated cryptographic R&D only  
**Base:** `codex/ripple-verification-federation-v1@dd1ca0d530cf81b02a4cf8c6de04c0b6727e029d`  
**Branch:** `codex/ripple-pq-migration-v1`

## 1. Purpose

This tranche adds a migration-safe post-quantum evidence profile without breaking the existing Node 22/24 verification contract.

The current federation baseline uses deterministic Ed25519 attestations as the portable signature root across both supported Node majors. Node 24.18 supports ML-DSA in built-in `node:crypto`, while Node 22 does not. Therefore v1 must not replace Ed25519 with ML-DSA or claim universal post-quantum verification.

Instead, v1 adds a **hybrid evidence envelope**:

- every authoritative federation attestation retains its existing Ed25519 signature;
- optional ML-DSA evidence may be attached to the exact same canonical unsigned attestation payload;
- Node 24 cryptographically verifies ML-DSA evidence;
- Node 22 validates structure, key/evidence commitments, and byte preservation but reports ML-DSA cryptographic verification as unavailable;
- hybrid status explicitly distinguishes integrity preservation from cryptographic verification.

This is a migration mechanism, not a claim that the entire system is post-quantum secure.

## 2. Standards and runtime boundary

The implementation targets the finalized NIST ML-DSA standard, FIPS 204, while recording the exact algorithm/profile identifier used by the runtime. The project must also record that FIPS 204 has a 2026 NIST errata planning note; implementation compatibility with a runtime is not equivalent to future-standard revision compliance.

Runtime capability contract:

```text
Node 22:
  Ed25519 sign/verify: supported
  ML-DSA sign/verify: unavailable in built-in crypto

Node 24.18:
  Ed25519 sign/verify: supported
  ML-DSA sign/verify: supported in built-in crypto
```

No dependency or polyfill is introduced merely to make Node 22 appear ML-DSA-capable.

## 3. Why ML-DSA signature bytes are not cross-runtime deterministic fixtures

FIPS 204 defines both hedged and deterministic signing, with hedged signing as the default. Node's high-level ML-DSA signing API does not expose a project-controlled `rnd` input that would let this repository force FIPS 204's optional deterministic variant.

Therefore:

- v1 does not require repeated ML-DSA signing to emit identical signature bytes;
- v1 never pins a freshly generated ML-DSA signature as though signing were deterministic;
- a **one-time Node-24-generated test evidence fixture** may contain fixed public/private test keys and a fixed already-generated signature, after which the signature is treated as immutable input evidence;
- Node 24 must verify that fixed signature cryptographically;
- Node 22 must preserve and hash the same signature bytes while returning `pq-unavailable`.

Ed25519 remains the deterministic cross-runtime signing fixture.

## 4. Capability manifest

`detectPqCapabilities()` returns a deeply immutable runtime-evidence object.

Required fields:

```text
capabilityVersion = pq-capabilities-v1
runtimeMajor
classical.ed25519 = supported
postQuantum.mlDsa = supported | unavailable
postQuantum.mlDsaProfiles = [ml-dsa-44, ml-dsa-65, ml-dsa-87] | []
postQuantum.slhDsa = supported | unavailable
claimClass = runtime-capability-observation
executionAuthority = none
```

The capability object is observational runtime evidence and is deliberately **not** content-identical between Node 22 and Node 24 because their capabilities differ.

A separate capability-policy object defines what the project accepts:

```text
requiredClassical = ed25519
optionalPostQuantum = ml-dsa-65
allowClassicalOnly = true
allowPqUnavailable = true
requireHybridForRelease = false
```

That policy remains R&D-only and grants no release authority.

## 5. ML-DSA test evidence profile

v1 uses a test-only ML-DSA-65 fixture generated once under supported Node 24 built-in crypto.

Fixture contains:

- explicit `TEST ONLY` warning;
- ML-DSA private key in PKCS#8 PEM or DER/Base64 form;
- ML-DSA public key in SPKI PEM or DER/Base64 form;
- public-key SHA-256 commitment;
- exact canonical unsigned federation attestation payload bytes hash;
- one fixed ML-DSA signature Base64 value generated by Node 24;
- fixed signature SHA-256 commitment;
- exact ML-DSA context bytes, if a context is used;
- declared algorithm `ml-dsa-65`.

The private key exists only to allow Node 24 test signing behavior to be exercised. It is never a production credential and never represents an independent reviewer.

## 6. PQ evidence envelope

`createPqEvidenceEnvelope(config)` is a pure content-addressing function available on both Node majors.

Fields:

```text
pqEvidenceVersion = pq-signature-evidence-v1
algorithm = ml-dsa-65
subjectAttestationHash
unsignedPayloadHash
publicKeySpkiBase64
publicKeyHash
signatureBase64
signatureHash
contextBase64
sourceRuntimeClass
claimClass = optional-post-quantum-signature-evidence
executionAuthority = none
pqEvidenceHash
```

This function performs structural/canonical validation and content addressing only. It does not itself claim cryptographic verification.

## 7. Runtime-specific ML-DSA verification

`verifyMlDsaEvidence(evidence, unsignedPayload)` returns one of:

```text
{
  disposition: "pq-verified",
  cryptographicVerificationPerformed: true,
  ...
}
```

on a capable Node 24 runtime, or:

```text
{
  disposition: "pq-unavailable",
  cryptographicVerificationPerformed: false,
  ...
}
```

on Node 22.

Both runtimes must still:

- recompute evidence content IDs;
- validate public-key and signature hashes;
- validate that `subjectAttestationHash` and `unsignedPayloadHash` match the supplied federation attestation;
- preserve exact PQ evidence bytes;
- reject malformed or stale evidence before runtime capability is considered.

Node 22 must never return `pq-verified`.

## 8. Hybrid attestation result

`evaluateHybridAttestation({ classicalAttestation, pqEvidence, registry, cryptoProfile, revocations })`

Always verifies the classical Ed25519 attestation through Federation v1 first.

Possible dispositions:

- `hybrid-verified` — Ed25519 verified and ML-DSA verified;
- `classical-verified-pq-unavailable` — Ed25519 verified; PQ evidence structurally valid but runtime cannot verify ML-DSA;
- `classical-verified-no-pq-evidence` — Ed25519 verified; no PQ evidence supplied;
- `invalid-pq-evidence` — classical verification succeeded but PQ evidence is malformed, mismatched, or cryptographically invalid on a capable runtime;
- classical federation errors propagate as failures and cannot be masked by valid PQ evidence.

Every result includes:

```text
classicalVerified: true
pqEvidencePresent: boolean
pqCryptographicallyVerified: boolean
postQuantumSystemSecurityClaim: false
executionAuthority: none
```

No hybrid result can grant merge, tag, deployment, cut-over, policy, or municipal authority.

## 9. Migration policy semantics

`evaluatePqMigrationPolicy(result, policy)` reports policy compliance separately from cryptographic disposition.

Examples:

- R&D policy may accept `classical-verified-pq-unavailable` on Node 22;
- a future hardened policy may require `hybrid-verified` on capable verification nodes;
- policy evaluation cannot change the underlying cryptographic facts;
- policy must never relabel `pq-unavailable` as verified.

No release policy in v1 is authoritative.

## 10. Test strategy

### Cross-runtime invariants

Node 22 and Node 24 must emit identical values for:

- classical Ed25519 attestation bytes/hash/signature fixture;
- fixed PQ evidence envelope bytes/hash;
- fixed ML-DSA public-key hash;
- fixed ML-DSA signature hash;
- unsigned payload hash;
- hybrid input commitment.

They are **expected to differ** only in runtime capability and resulting PQ verification disposition:

```text
Node 22 -> classical-verified-pq-unavailable
Node 24 -> hybrid-verified
```

That difference is an acceptance condition, not a conformance failure.

### Node 24 cryptographic gates

On Node 24:

- fixed ML-DSA-65 signature verifies;
- one-byte message mutation fails;
- one-byte signature mutation fails;
- wrong public key fails;
- wrong context fails, if context is used;
- newly generated ML-DSA signatures verify even if signature bytes differ between calls.

### Node 22 gates

On Node 22:

- ML-DSA evidence parses and content-addresses identically;
- runtime capability reports unavailable;
- no call path claims cryptographic verification;
- unsupported-key construction fails closed if attempted;
- no test is silently skipped merely because ML-DSA is absent.

## 11. Schemas and source boundaries

Add strict JSON Schema 2020-12 contracts for:

- PQ capability observation;
- PQ signature evidence;
- hybrid verification result;
- PQ migration policy/result.

New deterministic source lives under `src/pq/` and must be included in syntax and ambient-randomness source gates.

The PQ layer may import:

- federation verification APIs;
- canonicalization/immutability/errors;
- `node:crypto` for capability detection and Node-24 ML-DSA verification.

It must not import:

- simulation mutation APIs;
- branch mutation APIs;
- network clients;
- GitHub write APIs;
- wall-clock functions;
- ambient randomness directly.

Key generation/signing is isolated to test helpers or explicit fixture-generation tooling and is not used inside deterministic evidence identity.

## 12. Acceptance gates

1. Federation v1 inherited evidence remains green and unchanged.
2. Node 22 explicitly reports ML-DSA unavailable; Node 24.18 explicitly reports ML-DSA available.
3. Fixed PQ evidence hashes identically on Node 22 and Node 24.
4. Node 24 cryptographically verifies the fixed ML-DSA-65 evidence.
5. Node 22 does not cryptographically verify or claim PQ verification.
6. Classical Ed25519 verification is mandatory on both runtimes.
7. Invalid classical evidence cannot be rescued by valid PQ evidence.
8. Malformed/stale PQ evidence fails identically before capability-specific verification.
9. Invalid ML-DSA evidence on Node 24 produces `invalid-pq-evidence`.
10. The same invalid evidence on Node 22 remains structurally invalid rather than becoming `pq-unavailable`.
11. Hybrid result/policy artifacts are immutable, content-addressed, and schema-valid.
12. New source is syntax/randomness gated.
13. Complete Node 22/24 matrix passes with explicit expected runtime-difference assertions.
14. Verification report records the standards/runtime support boundary and no global PQ-security claim.

## 13. Explicitly deferred

Separate design/review cycles remain mandatory for:

- SLH-DSA hybrid support;
- portable ML-DSA verification on Node 22 or other runtimes;
- Rust/WASM/Python PQ conformance;
- production HSM/KMS key custody;
- certificate/PKI integration;
- algorithm deprecation and cryptoperiod governance;
- real external transparency-log/blockchain publication;
- zero-knowledge proofs;
- automated release enforcement based on hybrid verification;
- claims that the full Causal Operating System is post-quantum secure.

## 14. Claim boundary

Successful v1 implementation may support this statement:

> The project can attach ML-DSA-65 signature evidence to an existing Ed25519 federation attestation; Node 24 can verify the ML-DSA evidence using built-in crypto, while Node 22 preserves and validates the same evidence envelope but explicitly reports ML-DSA verification unavailable.

It may **not** support:

> The system is post-quantum secure.

That broader claim requires review of every cryptographic dependency, key lifecycle, storage channel, transport, identity mechanism, signature policy, external verifier, and long-term migration path.
